# QazTender Radar — передача проекта

Этот файл описывает текущее состояние QazTender Radar, чтобы другой разработчик или другая ИИ-платформа могли продолжить работу без переписки и скрытого контекста. Документ не содержит паролей, API-токенов, хешей паролей и личных данных.

## 1. Назначение продукта

QazTender Radar — личный рабочий сервис для поиска и отбора закупок Казахстана. Пользователь с ролью тендерщика заполняет профиль своей компании, видит подходящие объявления, сохраняет интересные закупки, ведёт этап участия и задачи. Главный администратор управляет аккаунтами тендерщиков и запускает загрузку официальных данных.

Главная бизнес-цель: не заменять официальный портал госзакупок, а помогать быстрее находить релевантные закупки, принимать решение об участии и не пропускать сроки.

Рабочий сайт опубликован приватно по адресу:

    https://qaztender-radar-demo.carmarew.chatgpt.site

## 2. Текущий статус

### Что уже реализовано

- Вход в приложение с собственной сессией.
- Роль главного администратора (`super_admin`), заданная серверными секретами.
- Роль тендерщика (`tender_specialist`), создаваемая только главным администратором.
- Страница управления тендерщиками: создание, просмотр и включение/отключение аккаунтов.
- Онбординг компании тендерщика. Обязательны название компании, минимум один регион и направление деятельности. БИН/ИИН, опыт, лицензии, число сотрудников и лимит бюджета необязательны.
- Выбор регионов и направлений работы вместо свободного ввода; поддерживается направление «все виды работ» и строительные подкатегории.
- Один верхний бюджет участия с вариантом «без ограничения».
- Главный радар закупок с поиском, фильтрами региона, вида предмета, бюджета, срока и признака строительных работ.
- Расширенный поиск по номеру объявления, заказчику/БИН, способу закупки, статусу, диапазону суммы, датам публикации и окончания, финансовому году и сортировке.
- Избранное и этапы работы с закупкой: просмотр, участвуем, заявка подана, выиграли, проиграли, пропустили.
- Сохранённые поиски и сохранение предпочтительной частоты уведомлений (`off`, `instant`, `daily`). Отправка уведомлений ещё не подключена.
- Профиль компании и объяснения соответствия по региону, бюджету, деятельности и лицензиям. Сайт намеренно не рисует неподтверждённые «проценты победы».
- Детальная основа для лотов, документов и истории изменений.
- Задачи по закупке: создание, назначение тендерщику, срок и отметка выполнения.
- Серверный клиент официального API госзакупок, защищённая синхронизация в базу и честное состояние «ожидается API-токен» вместо демонстрационных тендеров.

### Что пока не завершено

- Нет реальных записей закупок: требуется официальный API-токен портала госзакупок.
- Не выполнен первый реальный запуск синхронизации после получения токена.
- Не подтверждена на реальных данных загрузка лотов, документов и истории изменений.
- Нет фактической рассылки уведомлений в Telegram/email.
- Нет аналитики заказчиков/победителей и помощника по подготовке документов.

## 3. Самый важный следующий шаг: официальный API-токен

Данные должны поступать только через официальный GraphQL API портала госзакупок:

    https://ows.goszakup.gov.kz/v3/graphql

Токен хранится исключительно в серверном секрете `GOSZAKUP_API_TOKEN`. Его нельзя добавлять в Git, `.env` в репозитории, HTML, браузерный код, скриншоты, переписку или этот файл.

Текущий владелец проекта уже запросил первичный токен. Центр электронных финансов попросил направить подписанное сканированное письмо на имя АО «Центр электронных финансов» с исходящим номером и датой. После того как токен будет выдан:

1. Добавить значение токена в секреты хостинга под именем `GOSZAKUP_API_TOKEN`.
2. Не изменять исходный код ради токена.
3. Войти под главным администратором.
4. На главной странице нажать кнопку синхронизации.
5. Проверить, что появились реальные объявления, затем открыть несколько карточек и ссылки на официальный портал.
6. Проверить логи синхронизации и убедиться, что повторный запуск не создаёт дубликатов.

Приложение уже использует заголовок `Authorization: Bearer <token>` только на сервере. Данные сначала сохраняются в Cloudflare D1, затем отображаются пользователям. Браузер никогда не получает сам токен.

## 6. Роли и безопасность

### Роли

- `super_admin`: создаётся через серверные секреты, видит управление пользователями и может запускать синхронизацию с госзакупками.
- `tender_specialist`: учётная запись тендерщика, создаваемая администратором. Перед доступом к радару должен заполнить профиль компании.

Ни один маршрут браузера не должен принимать роль от пользователя. Роль определяется только серверной сессией.

### Серверные секреты и привязки

| Имя | Назначение |
| --- | --- |
| `DB` | Привязка Cloudflare D1. |
| `ADMIN_USERNAME` | Логин главного администратора. |
| `ADMIN_PASSWORD_HASH` | Хеш пароля главного администратора, не сам пароль. |
| `SESSION_SECRET` | Секрет подписи сессий. |
| `GOSZAKUP_API_TOKEN` | Официальный токен API; пока отсутствует. |

Никогда не переносить реальные значения этих переменных в код или документацию. При смене платформы надо создать новые защищённые переменные окружения и вручную перенести значения через панель секретов.

## 7. База данных

Основные таблицы:

- `users` — аккаунты тендерщиков, хеши паролей, активность.
- `company_profiles` — профиль компании одного тендерщика.
- `tenders` — нормализованные официальные объявления.
- `tender_lots` — лоты объявлений.
- `tender_documents` — метаданные официальных документов и ссылки.
- `tender_changes` — история обновлений после синхронизаций.
- `tender_workflow` — избранное и этап участия конкретного пользователя.
- `saved_searches` — сохранённые пользовательские фильтры и частота уведомлений.
- `tender_tasks` — задачи по закупке и назначенные исполнители.
- `tender_sync_runs` — журнал запусков синхронизации и ошибок.

Правило миграций: любые изменения схемы — только новой миграцией Drizzle. Не редактировать старые SQL-миграции на работающем проекте.

## 9. Данные и логика поиска

На первом этапе синхронизация читает объявления `TrdBuy` из V3 GraphQL. За один запуск приложение запрашивает до трёх страниц по 200 объявлений, то есть до 600 записей. Повторные загрузки обновляют существующие записи по официальному идентификатору, а не дублируют их.

Поддерживаемые фильтры объявлений:

- Текстовый запрос.
- Регион по КАТО.
- Предмет закупки.
- Верхний бюджет.
- Срок окончания.
- Только строительные работы.
- Номер объявления.
- Заказчик или БИН заказчика.
- Способ закупки и статус.
- Диапазон суммы.
- Диапазоны дат публикации и окончания.
- Финансовый год.
- Сортировка.

Важно: до получения токена интерфейс не должен показывать вымышленные «живые» тендеры. Пользователь должен видеть понятное состояние ожидания токена.

## 10. Рекомендуемый порядок дальнейшего развития

### Этап A — запуск реальных данных (критический)

1. Получить токен и добавить секрет `GOSZAKUP_API_TOKEN`.
2. Запустить синхронизацию вручную.
3. Исправить расхождения официальной схемы, если они обнаружатся на реальном ответе API.
4. Проверить фильтры на 20–50 настоящих объявлениях, особенно Туркестанскую область, бюджеты, сроки и строительные работы.
5. Настроить ограничение частоты синхронизаций, понятные ошибки API и журналирование.

Критерий готовности: администратор видит число полученных/сохранённых записей, тендерщик видит актуальные официальные объявления и может открыть исходную запись на goszakup.gov.kz.

### Этап B — точная подборка для компаний

1. Сделать прозрачную оценку соответствия профилю: регион, направления, бюджет, лицензии, сроки.
2. Показывать не «магический процент победы», а объяснение: почему объявление подходит и какие данные отсутствуют.
3. Добавить исключающие ключевые слова и список важных ключевых слов.
4. Дать пользователю возможность скрывать неподходящие объявления и учитывать это в будущей выдаче.

### Этап C — уведомления

1. Подключить один канал сначала: Telegram предпочтительнее для ежедневной работы.
2. Создать отдельный механизм отправки, таблицу доставок и журнал ошибок.
3. Отправлять только новые или существенно изменённые подходящие закупки.
4. Соблюдать выбранную пользователем частоту: сразу, раз в день, выключено.
5. Не отправлять токены, пароли, персональные данные или содержимое закрытых документов.

### Этап D — рабочее место тендерщика

1. Довести реальные лоты, ЕНС ТРУ, места поставки, документы и историю изменений до проверенной работы.
2. Добавить чек-листы по типам закупок и шаблоны задач.
3. Добавить комментарии/заметки к закупке и прикрепление внутренних файлов в отдельном защищённом хранилище.
4. Добавить календарь дедлайнов и напоминания.

### Этап E — аналитика и помощь с участием

1. Аналитика заказчика: прошлые закупки, суммы, активность, завершённые договоры — только по подтверждённым открытым данным.
2. Аналитика поставщиков и победителей — с понятным источником каждого факта.
3. Помощник по перечню требуемых документов: он должен ссылаться на конкретные документы закупки и явно отмечать, что требует проверки человеком.
4. Экспорт подборок в Excel/PDF только после определения требований к персональным данным и доступам.

## 11. Что не следует делать

- Не парсить закрытые страницы или обходить защиту официального портала.
- Не хранить токен в React-компонентах, localStorage, URL, репозитории или клиентском API.
- Не возвращать пароль/хеш пароля в JSON API.
- Не давать тендерщику создавать администратора или менять свою роль.
- Не подменять отсутствие данных демонстрационными закупками без явной маркировки.
- Не обещать вероятность победы без объяснимой модели и проверяемых источников.
- Не переписывать существующие миграции базы.

## 12. Перед началом работы на другой платформе

1. Скопировать весь репозиторий, включая `app/`, `db/`, `drizzle/`, `worker/`, `tests/`, `.openai/` и `docs/`.
2. Выполнить локальную сборку и тесты до любых изменений.
3. Настроить базу данных и применить все миграции в исходном порядке.
4. Перенести секреты только через защищённое хранилище новой платформы.
5. При необходимости перенести данные D1 отдельно: схема и исходный код сами по себе не перенесут пользователей, профили, сохранённые поиски и будущие закупки.
6. Сначала добиться реальной синхронизации, и только затем развивать уведомления и сложную аналитику.
